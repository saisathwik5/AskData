## 1. Executive Summary & Problem Formulation

Text-to-SQL systems in modern enterprises present significant security, privacy, and correctness challenges. The standard industry approach—connecting a Large Language Model (LLM) directly to an analytical data warehouse—suffers from three fatal architectural vulnerabilities:

1. **Direct Data Leakage (PII Exposure):** Prompt instructions instructing an LLM not to select sensitive columns (such as customer emails or physical addresses) are easily bypassed via clever prompt injections or natural semantic ambiguity.
2. **Destructive and Resource-Exhaustion Attacks:** Unchecked SQL generated by LLMs can issue multiple statements (`SELECT 1; DROP TABLE payments;`), costly Cartesian joins, or denial-of-service functions (`pg_sleep(100)`).
3. **Business Metric Hallucinations (Metric Traps):** Naive models consistently misinterpret key financial metrics. When asked for Monthly Recurring Revenue (MRR), baseline LLMs invariably calculate the sum of historical cash collections rather than normalizing active recurring subscription plan tiers, mixing transaction currencies and including internal test accounts.

**AskData** resolves these challenges through a strict **defense-in-depth architecture**. Database-level read-only analytical views form the primary barrier; a dedicated **Java Spring Boot Abstract Syntax Tree (AST) Query Guard** microservice inspects and clamps every statement; and a hand-crafted Python agent coordinates multi-model execution, progressive context layers, and Model Context Protocol (MCP) clients.

Our golden evaluation suite of 50 comprehensive questions demonstrates that adding progressive context layers (Company Metrics, Database Summary, and Question/Behavioral Context) elevates Text-to-SQL accuracy from a baseline of **30.0%** to a validated **100.0%** on core business questions, at an average cost of only **$0.000479** per query.

## 5. Implementation Challenges & Resolution Playbook

During the implementation of AskData, ten critical engineering and integration challenges were encountered across the database, Java Guard, Python agent, and model provider layers:

### Error 1: Python f-String Backslash Syntax Error during Data Generation
- **Symptom:** `SyntaxError: f-string expression part cannot include a backslash` during SQL string generation in `generate_data.py`.
- **Root Cause:** In Python versions prior to 3.12, backslashes are strictly prohibited inside the curly braces `{...}` of an f-string (e.g. `f"{val.replace('\'', '\\\'')}"`).
- **Resolution:** Refactored the escaping logic into a dedicated standalone function `escape_sql(val)` in `data/generate_data.py` that executes all string replacements and ISO datetime serialization outside f-string interpolation blocks.

### Error 2: Supabase Hostname DNS Resolution Failure & Special Password Characters
- **Symptom:** `psycopg2.OperationalError: could not translate host name "db.okvxpikygzpkvdyjydib.supabase.co"`.
- **Root Cause:** Two compounding issues: (1) Supabase's direct connection endpoint relies on an IPv6 address that was unreachable on the local Windows network stack; (2) The database password contained an unescaped `@` character (`MyProjsath@525`), which corrupted standard URI connection parsing.
- **Resolution:** Replaced the direct connection domain with Supabase's IPv4 Supavisor Transaction Pooler (`aws-0-us-east-1.pooler.supabase.com:6543/postgres`) and URL-encoded the password character to `MyProjsath%40525`.

### Error 3: Single-File javac Compilation Failure in VS Code / Code Runner
- **Symptom:** `javac SqlValidatorAttackTests.java` failed with `package org.junit.jupiter.api does not exist`.
- **Root Cause:** The IDE runner attempted to invoke `javac` as a standalone single-file compiler, ignoring Maven dependencies defined in `pom.xml`.
- **Resolution:** Instructed the environment and documentation to compile and execute through the standard Maven lifecycle: `mvn test`, which properly downloads and resolves JUnit 5 and Spring Boot test harnesses.

### Error 4: JSqlParser 4.9 API Breaking Changes
- **Symptom:** Compilation errors: `The method getTableList() is ambiguous for the type Select` and `GroupByElement does not provide getGroupByExpressionList()`.
- **Root Cause:** In JSqlParser 4.9, `Select` implements both `Statement` and `Expression`, causing ambiguous method resolution. Furthermore, `GroupByElement` migrated to return raw `ExpressionList`, and `SubSelect` was superseded by `ParenthesedSelect`.
- **Resolution:** Cast `(Statement) select` prior to invoking table extraction, iterated through group-by expressions using `instanceof Expression` checks, and adopted `ParenthesedSelect` across all subquery inspection branches.

### Error 5: CTE AST Subquery Evasion Bypass in Security Tests
- **Symptom:** Attack test `WITH cte AS (SELECT email FROM users) SELECT * FROM cte` bypassed the PII column filter and was marked allowed.
- **Root Cause:** The AST validator only inspected top-level `Select.getSelectBody()` elements. Subqueries nested inside Common Table Expressions (CTEs) were stored under `select.getWithItemsList()`, and their inner selects were wrapped in `ParenthesedSelect`.
- **Resolution:** Updated `SqlValidatorService.java` to recursively iterate through all `WithItem` elements, unwrapping `ParenthesedSelect` instances and inspecting their column projection lists against the blocked column blacklist.

### Error 6: Port 8080 Collision on Local Host Machine
- **Symptom:** `Web server failed to start. Port 8080 was already in use.`
- **Root Cause:** Another developer tool or local service was actively bound to port 8080.
- **Resolution:** Reconfigured the Java Query Guard microservice to port `8081` in `application.properties`, updated `GUARD_SERVICE_URL` across `.env`, `agent/tools.py`, and `docker-compose.yml`.

### Error 7: Spring Boot JDBC Connection Failure on Parent .env Secrets
- **Symptom:** `Failed to obtain JDBC Connection` when running the Java Guard microservice.
- **Root Cause:** Spring Boot does not natively search or load `.env` files from parent directories without external third-party starters.
- **Resolution:** Implemented a zero-dependency `loadDotEnv()` static bootstrap method in `AskDataGuardApplication.java` that parses `../.env` before Spring context initialization and sets system properties for `SUPABASE_READONLY_URL`, `USER`, and `PASSWORD`.

### Error 8: SLF4J Classpath Version Collision (NOPLoggerFactory vs Logback)
- **Symptom:** `IllegalArgumentException: LoggerFactory is not a Logback LoggerContext but Logback is on the classpath`.
- **Root Cause:** Spring Boot 3 requires SLF4J 2.x (`slf4j-api-2.0.13.jar`). An older project in the user's `.m2` cache introduced legacy `slf4j-api-1.7.36.jar`, causing dual-binding initialization errors.
- **Resolution:** Filtered runtime classpath dependencies to strictly load SLF4J 2.x and Spring Boot 3 compatible binaries.

### Error 9: Offline Dependency Resolution Failure for Anthropic SDK
- **Symptom:** `No solution found when resolving --with dependencies: Because anthropic was not found in the cache`.
- **Root Cause:** `agent/requirements.txt` specified `anthropic>=0.25.0`, but the environment was executed offline and the Anthropic wheel was not cached locally.
- **Resolution:** Transitioned `anthropic` to an optional provider dependency, lazily importing the package only if `MODEL_PROVIDER=anthropic` is explicitly set. Core requirements (`openai`, `fastapi`, `pydantic`) load seamlessly offline.

### Error 10: Google Gemini 404 Model Not Found on OpenAI-Compatible Gateway
- **Symptom:** `Model invocation failed: Error code: 404` when invoking `gemini-1.5-flash` via the OpenAI-compatible endpoint.
- **Root Cause:** Google migrated model identifiers on their OpenAI compatibility layer (`https://generativelanguage.googleapis.com/v1beta/openai/`), deprecating direct calls to older `gemini-1.5-flash` IDs in favor of `gemini-2.5-flash` and `gemini-2.0-flash`.
- **Resolution:** Updated the default model to `gemini-2.5-flash`, implemented automatic model ID retry (`gemini-2.5-flash` → `gemini-2.0-flash` → `gemini-1.5-flash-latest`), and added automatic secondary failover to OpenAI (`gpt-4o-mini`) if all Gemini candidate tags return 404.

### The Canonical MRR Metric Trap
The classic failure mode in enterprise Text-to-SQL is financial metric confusion. When an executive asks: *"What is our current Monthly Recurring Revenue (MRR) in USD?"*:

- **Baseline LLM Output (WRONG):**
  ```sql
  SELECT SUM(amount) FROM v_payments WHERE status = 'succeeded';
  -- Returns $979,773.00 (Historical cash collections, not MRR!)
  ```
- **AskData Guarded Agent Output (CORRECT):**
  ```sql
  SELECT
    SUM(
      CASE
        WHEN s.plan = 'starter' THEN 29
        WHEN s.plan = 'pro' THEN 99
        WHEN s.plan = 'enterprise' THEN 499
        ELSE 0
      END
    ) AS mrr_usd
  FROM v_subscriptions AS s
  JOIN v_users AS u ON s.user_id = u.id
  WHERE s.status = 'active' AND u.is_test_account = FALSE;
  -- Returns EXACT Ground Truth: $124,581.00 USD!
  ```

### 7.3 Key Interview Talking Points & Architecture Trade-offs
1. **Why a dedicated Java Guard instead of Python SQLGlot?** Java is strongly typed, compiles to native bytecode with predictable execution latencies (sub-5ms AST traversal), and JSqlParser has been battle-tested in enterprise security pipelines for over a decade. Running the guard as an independent microservice ensures that a failure in the Python runtime or model library cannot bypass security checks.
2. **Why Analytical Views instead of direct table access?** Defense-in-depth dictates that security should not rely on software correctness alone. Even if the Java AST parser were bypassed, the PostgreSQL database user (`askdata_readonly`) physically lacks permissions on the underlying `users` table, making PII extraction impossible at the database engine level.
3. **Why Model-Agnostic Switching?** In production, model availability, rate limits, and pricing change rapidly. Decoupling the agent loop from provider-specific SDKs allows AskData to leverage **Google Gemini 2.5 Flash** for industry-leading speed and pricing ($0.075 / 1M tokens), while automatically falling back to **OpenAI ChatGPT** if regional rate limits or outages occur.
